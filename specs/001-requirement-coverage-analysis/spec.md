# Feature Specification: 要件カバレッジの自動判定

**Feature Directory**: `specs/001-requirement-coverage-analysis`

**Created**: 2026-11-14

**Status**: Draft

**Input**: User description: "要件定義とE2Eテスト一覧（CSV）を突き合わせ、AIを用いて「どの要件がどのE2Eテストでカバーされているか」を自動判定・可視化する。検証用途（PoC）のMVPとして、実用性とコスト効率を最速で検証する。ファイルをアップロードすると判定が自動で始まり、結果のレポートが得られる。計算資源の課金は判定中だけに限る。"

## Clarifications

### Session 2026-11-14

- Q: 1つの要件は、どうなったら「カバーされている」と言えるか？ → A: 1件以上のテストが「確かめている」と判定されたら、カバーされている。
- Q: 各組の判定は、どんな値にするか？ → A: 「はい／いいえ」の2値。確信度を添える。
- Q: 想定する入力の最大件数は？ → A: 要件100件、テスト100件まで。
- Q: 判定が失敗したことを、利用者はどう知るか？ → A: 結果の置き場所に、失敗を示すファイルを置く。
- Q: 判定モデルは文章を作れない。理由はどう残すか？ → A: 理由の文章は作らず、確信度（0〜1）を根拠として残す。
- Q: 2つのCSVを1回の実行にまとめる方法は？ → A: 実行ごとのフォルダに、決まった名前（`requirements.csv`、`e2e-tests.csv`）で2つ置く。2つが揃ったら開始する。
- Q: 一部の組だけ判定に失敗したら？ → A: 1組でも失敗したら、実行全体を失敗にする。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - ファイルを置くだけでカバレッジのレポートが得られる (Priority: P1)

利用者は、要件のCSVとE2EテストのCSVを、決められた置き場所にアップロードする。
それ以降の操作は不要である。しばらくして、要件ごとの判定結果をまとめたレポートが、決められた場所に出る。

**Why this priority**: これが本MVPの価値のすべてである。この流れが通れば、要件の抜けを人手で探す作業をAIで置き換えられるかを検証できる。

**Independent Test**: サンプルの要件CSVとテストCSVを置き、レポートが出ることを確かめる。他の機能がなくても成立する。

**Acceptance Scenarios**:

1. **Given** 要件CSVとテストCSVが正しい形式である, **When** 2つをアップロードする, **Then** 追加の操作なしで判定が始まり、レポートが出力される。
2. **Given** 判定が終わった, **When** 利用者がレポートを開く, **Then** すべての要件について、カバーされているかどうかが分かる。

---

### User Story 2 - 要件とテストの対応を、確信度つきで確かめられる (Priority: P2)

利用者は、レポートで、各要件にどのテストが対応づけられたかと、その確信度を確かめる。
判定が妥当か、人が後から検証できる。

**Why this priority**: AIの判定を信用してよいかを検証することが、PoCの目的だからである。確信度がなければ、妥当性を評価しにくい。

**Independent Test**: レポートの1行ごとに、要件、テスト、判定、確信度が揃っていることを確かめる。

**Acceptance Scenarios**:

1. **Given** レポートが出ている, **When** ある要件の行を見る, **Then** その要件に対応するテストの一覧と、各組の判定と確信度が分かる。
2. **Given** どのテストにも対応しない要件がある, **When** レポートを見る, **Then** その要件は「カバーされていない」と明示される。

---

### User Story 3 - 課金は判定の間だけで、失敗しても続かない (Priority: P3)

運用者は、計算資源の課金が判定中だけに限られ、判定が失敗しても課金が続かないことを確かめる。

**Why this priority**: コストの低さは、PoCで検証したい点である。待機中の費用や、止め忘れの損失が出ない形にする。

**Independent Test**: 正常な実行と、わざと失敗させた実行の両方で、実行後に、課金が続く資源がないことを確かめる。

**Acceptance Scenarios**:

1. **Given** 判定が正常に終わった, **When** 終了を迎える, **Then** 課金が続く計算資源は残らない。
2. **Given** 判定の途中で失敗した, **When** 失敗を検知する, **Then** 課金が続く計算資源は残らず、失敗したことが分かる。

---

### Edge Cases

- CSVの列が足りない、または空である場合は、判定を始めず、原因が分かる形で失敗を知らせる。
- 要件またはテストが0件の場合は、レポートを作らず、その旨を知らせる。
- 同じ実行のフォルダに再度アップロードした場合は、新しい実行を始めず、前回のレポートを変えない。再実行は新しいフォルダで行う。
- 一方のCSVだけがアップロードされた場合は、もう一方が揃うまで判定を始めない。
- 1組でも判定に失敗した場合は、実行全体を失敗とし、部分的なレポートは出さない。
- 件数が多く、判定が長引く場合でも、上限の時間を超えたら失敗として止める。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、要件CSVとE2EテストCSVを入力として受け取らなければならない。
- **FR-002**: システムは、2つのファイルが揃ったときに、利用者の追加操作なしで判定を始めなければならない。
- **FR-003**: システムは、要件とテストのすべての組について、「その要件をそのテストが確かめているか」を判定しなければならない。
- **FR-004**: システムは、各組の判定を「はい／いいえ」の2値とし、その確信度（0〜1）を付けなければならない。理由の文章は作らない。
- **FR-005**: システムは、要件ごとに、「はい」と判定されたテストの一覧と件数を集計し、1件以上あればカバー済みとしなければならない。
- **FR-006**: システムは、判定結果のレポートを、利用者が取り出せる場所に出力しなければならない。
- **FR-007**: システムは、入力の形式が不正な場合、判定を始めずに、原因を書いた失敗ファイルを結果の置き場所に置かなければならない。
- **FR-008**: システムは、判定が正常に終わった場合も、失敗した場合も、判定のあとに課金が続く計算資源を残してはならない。
- **FR-009**: システムは、判定の実行ごとに、成功か失敗かが分かる記録を残さなければならない。失敗した場合は、失敗を示すファイルを結果の置き場所に置かなければならない。
- **FR-010**: システムは、実行の上限時間を超えた場合、その実行を失敗として終わらせなければならない。
- **FR-011**: システムは、実行ごとに別の場所へ結果を保存し、前回の結果を上書きしてはならない。

### Key Entities *(include if feature involves data)*

- **要件**: カバレッジを確かめたい1件の要求。識別子と説明を持つ。
- **E2Eテスト**: 1件のE2Eテスト。識別子と説明を持つ。
- **判定**: 1つの要件と1つのテストの組についての結果。「はい／いいえ」と、確信度を持つ。
- **カバレッジレポート**: 判定結果の集計。要件ごとに、対応するテストと、カバーの有無を持つ。
- **実行**: 1回の判定処理。入力ファイル、開始と終了、成功か失敗かを持つ。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 利用者は、2つのCSVをアップロードする以外の操作をせずに、レポートを得られる。
- **SC-002**: 要件100件、テスト100件の入力で、レポートが30分以内に出る。
- **SC-003**: レポートに載る要件の数が、入力の要件の数と100%一致する。
- **SC-004**: 人手で正解を付けたサンプルに対し、「カバーの有無」の判定が一致する割合を測定でき、PoCの評価に使える。
- **SC-005**: 正常終了と異常終了のどちらの実行でも、実行の終了後に、課金が続く計算資源が残っていない割合は100%である。
- **SC-006**: 待機中（誰も使っていないとき）の月額の費用が、数ドル以下である。

## Assumptions

- 利用者は、PoCの検証者に限られる。認証や権限の細かい管理は対象外とする。
- 入力はCSVのみとする。JSONへの対応は、このMVPの対象外とする。
- 各CSVには、識別子と説明の2つの列がある。ヘッダ行を持ち、文字コードは UTF-8 とする。列の名前は plan で決める。
- 判定の言語は日本語を主とする。
- 判定にはAWSの意思決定モデル（Strands Decider 2B）を使う。モデルの扱いは、plan で決める。
- 要件100件、テスト100件（最大1万組）までを対象とする。組み合わせの絞り込みは行わず、全組を判定する。これを超える入力は対象外とする。
- レポートの形式は、人が読めるものと、機械が読めるものの両方を出す。
- 並行して複数の実行が走る場合の扱いは、対象外とする。一度に1実行を前提とする。
- 本MVPは、検証用途とし、本番運用の可用性は求めない。
- 検証用のサンプルを `samples/` に置く。題材は、WEBの勤怠管理システムとし、E2Eテストは Playwright のテスト名の書き方に似せる。
  - `requirements.csv`: 架空の要件12件
  - `e2e-tests.csv`: 架空のE2Eテスト15件
  - `expected.csv`: 人が付けた正解の対応（SC-004の測定に使う）。要件のうち REQ-008、REQ-012 は、どのテストにも対応しない。
